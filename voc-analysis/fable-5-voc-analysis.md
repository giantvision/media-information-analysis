# 《信长之野望·真战》玩家原声（VoC）系统化分析框架
## —— 从实体抽取到多层级话题聚合的完整方法论与落地方案

---

## 一、背景与目标

本框架服务于《信长之野望·真战》（率土like SLG + RPG 融合玩法，《三国志·战略版》同源团队产品）的用户行为研究，目标是：

1. 对海量用户原声（游戏内反馈、客服工单、问卷、社区/贴吧/NGA/Discord/X/巴哈姆特、应用商店评论、直播弹幕等）建立一套**严谨、稳定、可演进的层级话题体系（Taxonomy）**；
2. 在「每条原声已由 LLM 抽取出关键实体 + 一句话话题摘要」的现状之上，支持**自底向上的话题聚合**与**自顶向下的标签挂载**双向打通；
3. 支撑后续的舆情监控、版本对比、问题预警、需求挖掘、流失归因等分析场景。

### 1.1 游戏域特征（决定框架必须覆盖的内容）

《信长之野望·真战》及其所属的「真战/率土like」品类，玩家原声高度集中在以下结构性特征上，这是设计 Taxonomy 的领域依据：

- **赛季制大地图争夺**：以地块（土地）争夺为核心交互，赛季更替、剧本规则、资源州/洲争夺、鬼服与服务器生态问题是长线舆情主阵地；
- **同盟社交结构**：指挥层/平民/大R 分工协作，同盟管理、外交、集结、内鬼/演员等社交话题量大且情绪强烈；
- **卡牌+战法养成**：抽卡概率、限定卡、武将强度、战法搭配、兵种克制、典藏/传承等付费与平衡话题是付费舆情核心；
- **"不卖资源不卖兵"的公平性承诺**：玩家对数值公平、零氪生态、付费深度的感知极其敏感，是品牌口碑的生命线；
- **RPG 融合玩法（本作差异点）**：城主出身选择、六艺修炼（武艺/辩才/茶道/算数/锻冶/建筑）、NPC 交友与信物、技艺小游戏、体力与汉方药机制——这是本作区别于三战的新增舆情面；
- **历史考据与 IP 情怀**：信长之野望 IP 受众对武将立绘、史实还原、地理格局、家族/势力设定有强烈的考据型反馈；
- **强时间投入（肝度）与多端体验**：日常操作负担、扫荡/托管诉求、跨端与机型适配等。

## 二、框架总体设计：多维正交标签体系（非单一树）

### 2.1 核心设计原则

1. **「对象域树 + 横向维度」分离**：一条原声同时回答多个问题——*在说什么（What，对象域树）*、*想干什么（Why，意图）*、*感受如何（情感/强度）*、*谁在说（玩家画像）*、*何时何处说（渠道/版本/赛季）*。如果把"抽卡概率低""建议优化抽卡 UI""抽卡时闪退"塞进同一棵树，树会爆炸且不稳定。**树只建模游戏对象域，其余全部做成正交维度标签。**
2. **层级深度固定为 4 层**：L1 领域(Domain) → L2 系统(System) → L3 功能/玩法点(Feature) → L4 实体(Entity)。L1–L3 由人工定义、低频演进（保证跨版本可比）；L4 是开放集合，由实体抽取自动填充、靠别名词典归一。
3. **MECE 优先 + 多标允许**：L1–L3 尽量互斥完备；单条原声允许挂多个 L3 节点（玩家一句话常横跨"武将强度+抽卡概率"）。
4. **每个节点有定义、正反例与边界说明**：这是 LLM 分类提示词的直接素材，也是人审一致性的依据。
5. **预留「其他/未归类」桶并定期挖掘**：新话题（新剧本、新活动、突发事件）从未归类桶中经聚类涌现，再人工晋升为正式节点——保证体系"活着"。

### 2.2 六个标注维度总览

| 维度 | 性质 | 取值结构 | 来源 |
|---|---|---|---|
| D1 对象域 | 层级树 | L1→L2→L3→L4 | LLM 分类 + 实体挂载 |
| D2 反馈意图 | 扁平枚举(可二级) | Bug反馈/建议/抱怨/咨询/赞扬/对比/求助/流失信号/纯情绪宣泄 | LLM 分类 |
| D3 情感与强度 | 量表 | 极性(正/中/负) × 强度(1–3) × 是否含流失/退款/差评威胁 | LLM 分类 |
| D4 玩家画像 | 多选标签 | 生命周期(新手/开荒/成长/成熟/回流/流失)、付费层(零氪/微氪/中R/大R，可由内部数据回填)、生态角色(指挥/团长/平民/独狼) | 内部数据关联 > 文本推断 |
| D5 渠道与场景 | 元数据 | 渠道、语言/地区、版本号、赛季/剧本、服务器、事件锚点 | 数据采集层 |
| D6 体验属性 | 多选标签 | 公平性/平衡性/易用性/性能稳定/付费价值感/社交体验/内容新鲜感/肝度负担/考据沉浸 | LLM 分类（横切 D1） |

> D6 是给管理层做"体验健康度"汇总的横切面：同一个 L3 节点（如"卡池"）可以分别统计其"公平性"与"付费价值感"两个属性下的负面占比。

## 四、横向维度详表

### D2 反馈意图（单选主意图 + 可选次意图）

| 代码 | 意图 | 定义与判别要点 |
|---|---|---|

| I5 | 赞扬认可 | 正面评价、感谢、安利 |
| I6 | 对比讨论 | 与竞品/历史版本/原作系列对比 |
| I7 | 流失/付费风险信号 | 明示退坑、卸载、停氪、退款、差评意向 |
| I8 | 举报投诉 | 针对其他玩家/工作室/客服的投诉 |
| I9 | 情绪宣泄/灌水 | 无具体对象的情绪或闲聊（低分析价值，需留存计数） |

### D3 情感：极性 {正/中/负} × 强度 {1轻微, 2明确, 3激烈} × 风险旗标 {退坑, 退款, 公开差评, 群体性事件}

### D6 体验属性（多选，用于健康度仪表盘）
公平性 | 平衡性 | 易用性/操作效率 | 性能稳定 | 付费价值感 | 社交体验 | 内容新鲜感 | 肝度负担 | 沉浸/考据 | 安全信任

## 五、技术路线分析：从「实体+摘要」到层级聚合

### 5.1 三条候选路线对比

| 路线 | 代表 | 做法 | 优点 | 风险 |
|---|---|---|---|---|
| A. 纯 embedding 聚类 + LLM 命名 | BERTopic（+HDBSCAN/UMAP）、GitHub 客服反馈实践 | 摘要向量化→密度聚类→LLM 给簇命名 | 无监督、能发现未知话题 | 簇不稳定、跨批次不可比、层级不严谨、簇粒度难控 |
| B. 纯 LLM 生成式分类法 | TnT-LLM(Microsoft)、TopicGPT、LLMTaxo | LLM 先从摘要样本归纳/迭代精炼 taxonomy，再用 LLM/轻量分类器全量挂载 | 标签可读性强、人可干预 | 全量成本高、taxonomy 漂移、对采样敏感 |
| C. **混合：人工种子 Taxonomy + LLM 挂载 + 聚类发现新话题（推荐）** | 本框架 | 第三章大纲作为种子树；LLM 把每条「实体+摘要」挂载到 L3；未归类桶定期跑 BERTopic 式聚类，候选新节点人审晋升 | 跨版本可比、领域可控、保留发现能力 | 需要维护节点定义与别名词典 |

> 选 C 的核心理由：运营分析最怕"上月的话题和这月对不上"。固定 L1–L3 保证时序可比性；开放 L4 + 未归类挖掘保证不漏新事件。这也与 TnT-LLM"先生成分类法、再规模化挂载"的两阶段思想一致，只是把第一阶段换成「领域种子树 + 数据驱动修订」。

### 5.2 推荐 Pipeline（在你们现有产出之上增量构建）

```
现有: 原声 → LLM 小结 → {关键实体[], 话题摘要}
                              │
┌─────────────────────────────┼──────────────────────────────┐
│ ① 实体归一化层               ▼                              │
│   别名词典: 武将名(信长/第六天魔王/织田)、黑话(演员/门神/    │

├──────────────────────────────────────────────────────────────┤
│ ② 多维标注层（一次 LLM 调用产出结构化 JSON）                 │
│   输入: 摘要 + 归一化实体 + 候选 L3 列表(由实体先验映射 +     │
│   embedding 召回 Top-K 节点缩小候选，控制 prompt 成本)        │

├──────────────────────────────────────────────────────────────┤
│ ③ 聚合层                                                     │

│   统计: 声量、负面率、强度加权净情感、环比突增(z-score)、     │
│   代表原声 Top-N(MMR 选多样性样本) + LLM 周报摘要             │
├──────────────────────────────────────────────────────────────┤
│ ④ 新话题发现层（周期任务）                                   │
│   未归类桶 + 各节点内异常增量 → embedding 聚类(HDBSCAN)       │
│   → LLM 命名+定义 → 人审 → 晋升为新 L3/L4 或合并入现有节点    │

├──────────────────────────────────────────────────────────────┤
│ ⑤ 评估与治理层                                               │
│   - 挂载准确率: 分层抽样人审(每节点≥30条), 目标≥85%           │
```

## 六、落地路线图

**Phase 1（1–2 周）冷启动**：定稿 L1–L3 树 v1.0（以第三章为底，用 5k 条历史原声抽样校验覆盖率）；建第一版实体别名词典（武将全名/绰号、黑话 200 词起步）；写好每个 L3 节点的定义+正反例。

**Phase 2（2–4 周）批量挂载**：跑通 ②③ 层，全量历史数据打标；上线人审抽检与一致性评估；产出首张「领域×情感×意图」基线大盘。

**Phase 3（持续）运营化**：周级新话题发现与 taxonomy 修订例会；接入版本/赛季锚点做事件归因（如新剧本上线前后 L1-03 负面率变化）；突增预警（z-score>3 自动推送）；按 D4 画像分层看板（大R 与零氪对"付费公平"的感知差）。

**Phase 4（优化）降本提效**：用已积累的高置信标注数据蒸馏小模型/微调 embedding 分类器，替换 80% 的 LLM 挂载调用，LLM 只处理低置信与未归类样本。

### 关键风险提示
1. **黑话与讽刺**：SLG 社区高密度反讽（"策划牛逼""真公平啊"），情感判别 prompt 必须带反讽 few-shot；
2. **群体性事件污染**：差评轰炸/有组织控评会扭曲声量，需做去重(近重复检测)与水军特征过滤后再统计；
3. **内外数据口径**：游戏内反馈偏 Bug/客服，外部社区偏平衡/付费/口碑，仪表盘必须分渠道呈现再合并，避免辛普森悖论；
4. **taxonomy 政治化**：节点命名避免预设结论（用"付费深度争议"而非"逼氪"），保持中性以便长期跨团队使用。
